# 測試計畫

實作順序就是這份清單的順序。每一顆走完 CLAUDE.md 的完整循環：
寫一顆紅燈 → 停下來給使用者審 → 核准後單獨 commit 測試 → 實作到剛好變綠
→ commit 實作 → 自動進入下一顆。

這份清單**不是架構設計**。「逼出什麼」欄位寫的是預期，不是承諾；
實際長出什麼由測試決定，事後與這裡不符是正常的。

## 開工前的兩個決定

- **測試資料庫的隔離方式**：第一顆碰 DB 的測試（#2）就採用
  `beforeAll` 建立一次實例 + 每顆測試 `BEGIN` / `ROLLBACK` 的形狀。
  不在那之前先改 `createTestDatabase()`，也不拖到測試變多才改。
- **`createApp()` 的簽名**：目前無參數。#2 會逼出 `createApp(db)`，
  屆時 #1 的測試跟著改一行。這比現在先加參數乾淨。
- **住民 seed**：放進 migration。測試資料庫套用同一份 migration 就自動
  有這 5 筆，測試與正式環境的住民資料保證一致。
- **順序**：後端 16 顆全部做完，再做前端 7 顆。前端用 MSW 攔網路層，
  不需要等後端，但契約若在實作中發現有洞，改一次比改兩邊便宜。

## 後端

| # | 紅燈 | 預期逼出什麼 |
|---|---|---|
| 1 | `GET /api/patients` 回 200，body 是陣列 | 路由存在（實作可以就回 `[]`） |
| 2 | 回傳 5 位住民的 `id` 與 `name` | patients 資料表 migration、seed、Kysely 查詢、`createApp(db)` |
| 3 | 住民存在但無醫囑 → `200 []` | orders 資料表、住民存在性檢查 |
| 4 | 住民不存在 → `404 NOT_FOUND` | 錯誤信封與 error middleware |
| 5 | `/patients/abc/orders` → `400 VALIDATION_FAILED` | 路徑參數驗證 |
| 6 | `POST` 合法 → `201` + 建立的醫囑 | insert |
| 7 | `POST` message 為空 → `400`，`data.message` 是陣列 | body 驗證 |
| 8 | `POST` 帶未定義欄位 → `400`，`data` 帶該欄位名 | zod `.strict()` |
| 9 | `POST` 住民不存在 → `404` | |
| 10 | 多筆醫囑依建立時間由舊到新 | 排序依據（DB 需要時間欄位，契約不暴露） |
| 11 | `PUT` 合法 → `200` + 改寫後內容 | update |
| 12 | `PUT` 醫囑不存在 → `404` | |
| 13 | `PUT` 驗證失敗 → `400` | |
| 14 | 打不存在的路徑 → `404 ROUTE_NOT_FOUND` | fallback route |
| 15 | body 不是合法 JSON → `400 VALIDATION_FAILED` | `express.json()` 的解析錯誤接進信封 |
| 16 | 未預期錯誤 → `500 INTERNAL_ERROR`，message 是固定字串 | error middleware 兜底與遮蔽 |

#4、#14、#15、#16 是錯誤信封的四個面向，分成四顆是刻意的：它們走的是
不同路徑（handler 丟出、路由未命中、middleware 丟出、未知例外），一顆測不完。
